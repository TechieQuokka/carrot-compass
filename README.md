# CarrotCompass

의뢰 기반 IT 기업을 위한 월급 배분 수식입니다. 정밀한 분배 계산기라기보다 **회사가 원하는 행동을 직원에게 간접적으로 알려주는 신호 장치**를 목표로 합니다. 직원이 수식을 보고 "무엇을 하면 보상이 커지는지" 읽을 수 있어야 합니다.

## 설계 원칙

- **안정적인 급여**: 기본급(최저임금 + 직급 가산)은 고정이고, 이번 달 수익에 따라 변하는 건 상한이 있는 성과급뿐입니다.
- **fact 우선, 주관은 제한**: 수집 가능한 사실(Git, 이슈 트래커, 근태, 회계)이 결과를 대부분 결정하고, 사람의 판단은 범위가 제한된 미세 조정에만 씁니다.
- **어려운 일은 더 받고, 쉬운 일은 덜 받는다**: 난이도는 manager의 주장이 아니라 측정 가능한 흔적으로 추정합니다.
- **투명성**: 모든 항목이 한 줄로 설명되어야 "왜 이 금액인지" 답할 수 있습니다.

## 입력의 두 종류

| 구분 | 의미 | 예시 |
|---|---|---|
| **일반 파라미터 (fact)** | 자동으로 수집되는 값 | 직급, 근무비율, 투입 시간, 수정 파일 수, 복잡도, 리뷰 왕복 수, 유효 코드량, 해결한 버그, 결함 수, 수익, 비용 |
| **하이퍼파라미터 (HP)** | 사람이 입력하는 주관값, 항상 clamp 적용 | PR 난이도 보정 `u` (0.85~1.15), 인물 보정 `e` (0.9~1.1) |

커밋 수는 점수에 **넣지 않습니다.** 쪼개 올리면 쉽게 늘어나는 지표라서, 이상 탐지용 필드로만 보관합니다.

## 수식

```
1. Base_i     = (M + alpha * L_i) * H_i

2. D_auto     = 1 + a*n_파일 + b*n_복잡도 + c*n_리뷰왕복          (a+b+c = 1, n은 0~1)
   D_final    = clamp(D_auto * u_pr, 1.0, 2.0)

3. 산출_i     = Σ_PR sqrt(유효LOC) * D_final
   품질_i     = max(0, Σ(해결한 버그 심각도, 본인이 만든 버그 제외) - 감점 * 결함 수)
   시간_i     = 투입 시간,   협업_i = 리뷰·페어·문서화 가중 건수
   s_i        = l1*r(산출) + l2*r(품질) + l3*r(시간) + l4*r(협업)   r = 프로젝트 내 내 비율

4. raw_i      = m_i * s_i                      (main이면 m_main, sub이면 1)
   share_i    = raw_i / Σ raw_j
   share'_i   = (1 - eps) * share_i + eps / n   (평균 쪽으로 당김)

5. Pool_raw   = theta * max(0, ΣProfit_p - C_fixed - ΣBase)
   Pool       = 0.5*Pool_raw(t) + 0.3*Pool_raw(t-1) + 0.2*Pool_raw(t-2)
   c_i        = Σ_p Profit_p * share'_{i,p}
   Bonus_raw  = Pool * c_i / Σ c_j

6. e_i        = clamp(TrimmedMean(평가자 점수), 0.9, 1.1)
   Bonus_i    = clamp(Bonus_raw * e_i, 0, kappa * Base_i)
   초과분      → 적립금(reserve)

7. Salary_i   = Base_i + Bonus_i
```

## 악의적 입력 방어

| 위험 | 방어 장치 |
|---|---|
| 점수를 높게/낮게 조작 | 모든 사람 입력은 양쪽 모두 clamp (`u`, `e`) |
| 한 평가자의 편향 | 절사평균(최고·최저 제거). 평가자 3명 미만이면 보정은 중립(1.0) |
| 난이도 조작 | `D` 상한 2.0, 사람 보정은 ±15%까지만 |
| 코드량 부풀리기 | `sqrt(LOC)` 사용, 커밋 수는 점수 미반영 |
| 자기가 낸 버그를 고쳐 점수 받기 | 본인이 만든 버그는 버그 수정 점수에서 제외, 결함은 감점 |
| 월급 변동성 | 풀을 3개월 평활화, 성과급은 `kappa * Base` 상한, 초과분은 적립 |

최악의 경우에도 개인의 성과급은 `kappa * Base_i` (기본값 기본급의 40%)를 넘지 않습니다.

## 파일 구성

```
salary_formula.py   # 구현 + 샘플 시뮬레이션
README.md
```

`salary_formula.py`의 주요 구성:

| 항목 | 역할 |
|---|---|
| `Config` | 하이퍼파라미터 초기값 모음 |
| `PR`, `Contribution`, `Employee`, `Project` | 수집되는 fact의 데이터 모델 |
| `LEVEL_TITLES` | 직급명 (L1 Associate, L2 Junior, L3 Mid, L4 Senior, L5 Lead) |
| `pr_difficulty` | 2단계 |
| `project_shares` | 3~4단계 |
| `person_adjustment` | 6단계의 사람 보정 |
| `settle_month` | 1, 5, 6, 7단계를 포함한 월 정산 전체 |

## 사용법

Python 3.9 이상이 필요하고, 표준 라이브러리만 사용합니다.

```bash
python3 salary_formula.py
```

실제 데이터에 쓰려면 Git, 이슈 트래커, 회계 자료에서 `Employee`와 `Project` 객체를 만들어 호출합니다.

```python
from salary_formula import Config, settle_month

result = settle_month(
    employees,
    projects,
    fixed_cost=15_000_000,
    pool_history=[pool_raw_t2, pool_raw_t1],   # 과거 Pool_raw, 오래된 순
    cfg=Config(),
)
```

## 튜닝 가이드

- **상한 도달 빈도 확인**: 평범한 달에 대부분이 `kappa` 상한에 걸리면 난이도 차이가 월급에 드러나지 않습니다. 상한은 수익이 유난히 좋은 달에만 걸리도록 `theta`와 `kappa`를 맞추세요.
- **도입 전 시뮬레이션**: 실제 또는 과거 데이터 몇 개월 치로 `theta`, `kappa`, `eps`를 바꿔가며 월급 분포를 비교하세요.
- **정규화 기준(`diff_caps`)**은 임의값입니다. 실제 PR 통계에 맞춰 보정하세요.
- **풀과 지급 총액**: 인물 보정은 풀을 나눈 뒤에 곱해지므로 지급 총액이 풀과 조금 다를 수 있습니다. 차이는 적립금으로 흘러갑니다.

## 한계와 주의사항

- 수집되는 데이터의 품질이 곧 결과의 품질입니다. 지표에 노이즈가 많으면 월급에도 노이즈가 반영됩니다.
- 프로젝트 외 업무(영업, 채용, 내부 도구 등)는 아직 반영되지 않아, 별도의 보상 경로가 필요할 수 있습니다.
- 수익 인식 방식(발생주의 vs 현금주의)은 이 버전에서 정하지 않았습니다.
- 한국에서는 정기적·일률적으로 지급되는 성과급이 통상임금으로 판단될 수 있어 연장수당과 퇴직금 산정에 영향을 줄 수 있습니다. 도입 전에 노무사의 검토를 받으세요. 이 문서는 법률 자문이 아닙니다.
